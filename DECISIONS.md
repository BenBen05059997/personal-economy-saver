# Decisions

The current decisions, and only those. When PLAN.md, AGENTS.md, ARCHITECTURE.md or any other document disagrees with this file, this file wins and the other gets fixed.

How it is kept: when a decision changes, its row is rewritten to the new decision (or deleted if it no longer applies). Nothing old is kept. The row is updated in the same turn the decision is made, then any document that still says the old thing is fixed.

| D10 | **Inputs:** a forwarding address and photo/PDF upload (one or several files at a time). One reader for bills, card-use emails and receipts. | D32 | **The app runs on Cloudflare Workers** through the OpenNext adapter, with `cacheComponents` and `partialPrefetching` on and the read-only static-assets incremental cache (the default dummy cache hangs the prerendered page). | D33 | **AI keys are the household's, stored in Supabase Vault; no model call is capped.** A household that chooses its own model (D56) gives its key in Settings → Your AI model; it is sent once over HTTPS, **sealed** in the Worker with AES-GCM under `AI_KEY_SEAL_KEY` (a Worker-only secret of 32 random bytes as unpadded base64url, like `MCP_TOKEN_KEY`; the household id is bound in as associated data, so a sealed text copied to another household does not open; stored as `pes-ai1.` plus the base64url of the IV and ciphertext, `sealAiKey` and `unsealAiKey` in `src/db/ai-key.ts`) and then stored with `vault.create_secret`, so it is encrypted with a key Supabase keeps outside the database as well; `households.ai_key_secret_id` points at it and `ai_key_hint` shows only its last four characters. It is never logged or returned to the browser. The owner's connection in the server settings (`AI_PROTOCOL`, `AI_BASE_URL`, `AI_API_KEY`, `AI_TEXT_MODEL`, `AI_DOCUMENT_MODEL`) is the **default**; neither it nor a household's own connection has a daily cap or an app-wide budget (the owner's choice, Nov 8). Missing settings fail clearly. A key saved before sealing existed is refused with "Your saved AI key predates sealed storage. Save your key again in Settings.", never read as a key. Vault ownership is checked by household-bound secret name, and reset, upgrade and deletion remove the household key and private documents with retryable database pointers. Document reads and Ask call the model; MCP engine tools do not. This is the monetisation line: free with your own model, a paid plan when we carry the AI cost. Judges never need it. | Pay-per-use AI is the only real cost; users of a money app expect to control it. Vault covers a leaked dump or backup; the second seal, whose key lives only in the Worker, also hides keys from someone holding the database's master credentials, who can read `vault.decrypted_secrets` but not the sealed text's contents. |

| D36 | **Reading pipeline.** Upload a photo/PDF or forward to the household’s opaque address. Store the original in a private bucket, return after queuing, and read it in the background through the request’s lifetime hook. The connection's document model (`AI_DOCUMENT_MODEL`, or the household's own, D56) reads photos, PDFs and mail with attachments; its text model (`AI_TEXT_MODEL`, or the household's own) reads plain mail. Validate extracted fields, run the checks of D61 on them, and show both in To check, and in Ask when the file was attached there. Confirmation creates a bill or card charge. Rule patches carry forward corrected names, categories, entry types and cards. Amount and date edits apply to the individual document. Reads are not capped (D33), and neither are uploads and retries: there is no per-minute limit, because it refused a person's seventh file instead of waiting and forwarded emails shared it, so a burst of card emails could lose a bill. What guards a file is its size (6 MiB), the storage cap (D37), a household session or the Worker's secret, and one document per identical file (`contentId`). Upload and Ask's Attach a bill take several files at once; each is sent on its own, one after another, and a refused file does not stop the others. | Nothing enters the numbers before confirmation. Model selection and the forwarding domain require explicit settings. |
| D37 | **Freshness and safety details.** Home refreshes only locally associated sandbox invoice IDs, with a five-minute cooldown that includes failed attempts. Only the designated non-demo household (`PAYPAL_BALANCE_HOUSEHOLD_ID`) can pull the merchant’s available balance. Other households use their own verified credits. Report timestamps and verified payment timestamps prevent stale reports from erasing receipts or counting them twice. A read can close a cancelled invoice. Only a verified webhook marks it paid. Home renders stored amounts with an explicit status when refresh fails. Demo receipts keep the provider’s timestamp in Activity and use a business date no earlier than the scenario date or the invoice send date. Approve carries an idempotency key per draft. Mutating routes check the origin; cookies are same-site. MCP tokens are made in Settings, shown once, stored hashed, revocable, read and draft only. Sign-in links return to `APP_URL` (required setting), never to the request's Origin header; a missing `APP_URL` raises a clear error. The AI-key route caps its body at 4 KiB by reading the stream, not by trusting Content-Length. The hourly trigger selects at most 30 non-demo households for separate daily or reminder requests (D64). It generates `card_statements` rows on each card's closing day from confirmed charges. | D43 | **Planning is pots.** A pot is money set aside with a reason: a name, a target amount and date (optional), the amount saved so far, an optional fill rule (a percentage of each client payment) and an optional member.
