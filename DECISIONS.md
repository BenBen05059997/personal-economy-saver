# Decisions

The current decisions, and only those. When PLAN.md, AGENTS.md, ARCHITECTURE.md or any other document disagrees with this file, this file wins and the other gets fixed.

How it is kept: when a decision changes, its row is rewritten to the new decision (or deleted if it no longer applies). Nothing old is kept. The row is updated in the same turn the decision is made, then any document that still says the old thing is fixed.

### How it works

| ID | Decision | Why |
|---|---|---|
| D10 | **Inputs:** a forwarding address and photo/PDF upload. One reader for bills, card-use emails and receipts. Every read goes through a confirmation card; corrections become rules. No Gmail OAuth, no bank or card login; the only account connection is PayPal (the model a household chooses is D56). | Privacy; Gmail read scope needs review and caps test users. |
| D11 | **Runway:** 30 days. Cash = PayPal balance + typed bank balance. Out = bills and card statements on their due dates. In = invoices at expected (sent + the client's median days to pay) and worst case (sent + their slowest). Alerts fire on the worst case. USD households' invoice forecasts round to cents, not whole dollars. | Believable, computed from PayPal history; fits one screen. |
| D12 | **The PayPal action is getting paid, not paying bills:** invoice finished work, remind late clients. The agent holds only draft/read tools (the toolkit's draft/send split is the approval gate); send and reminders run server-side after the user taps Approve. A verified webhook closes the loop. Lint enforces the split: only `src/app/api/approve/route.ts` may import the send-capable `runTool` and `deleteSmokeDraft` (`no-restricted-imports` in `economy-saver/eslint.config.mjs`). | Billers aren't PayPal merchants; getting paid is where PayPal is strongest. |
| D13 | **Agent Toolkit used directly** (`PayPalAPI.run()` + tool definitions), not its AI SDK wrapper. The toolkit has no balance or webhook tools, so the balance is a direct REST read (`/v1/reporting/balances`) and webhook verification is a direct REST call. `create_invoice` makes a draft with no due date or payment term, so the expected payment date is the send date plus the client's observed days to pay. Tool errors come back as JSON strings and are shown as they are. | The wrapper is pinned to an old AI SDK. |
| D14 | **Sandbox only, enforced in code.** AGENTS.md rule 1, enforced in `src/lib/env.ts`; the toolkit is created with `sandbox: true`. | Safety; the toolkit defaults to live. |
| D15 | **Webhooks are verified** with PayPal's signature check before anything changes. A verified delivery, the fully paid invoice transition and its notification commit together. Deliveries are unique on PayPal event id. Partial or pending payments leave the invoice open. The browser never sets payment state. | Trust. |
| D16 | **PayPal fee framing:** help the user keep more of each payout (price the fee in, invoice currency, convert in bulk). Never "leave PayPal". | Biggest single cost for a foreign-paid freelancer; PayPal-judged contest. |
| D17 | **Sandbox setup:** the app "Personal Economy Saver" is on the **Japan Business** sandbox account (Ben); the **US Personal** sandbox account is the client who pays. | How the owner's dashboard is set up. |

| D31 | **The record lives in Supabase** (free tier), in Northeast Asia (Tokyo, `ap-northeast-1`) through the transaction pooler on port 6543, because the users and Cloudflare's nearest edge are in Japan: Postgres through Drizzle, magic-link login through Supabase Auth, uploads (receipt photos, PDFs, forwarded emails) in Supabase Storage. Memory, pinned canvases and conversations live there too unless the household keeps them on one device (D59). The tables are listed in ARCHITECTURE.md. Household data queries require `household_id`; verified deliveries for an unknown invoice can be recorded without a household and do not affect money state. Money is integer minor units plus currency, never floats; the FX rate is stored on each conversion; webhook_deliveries is unique on PayPal's event id; "the 27th" is the household's time zone. One PayPal merchant via env keys (per-user Connect with PayPal needs partner approval); `paypal_connections` is per member and has a `merchant_id` column, so per-user Connect is later a change of source, not a rewrite. A delete-my-household route exists. | One free account gives database, login and files; no card needed. Integer money and idempotent webhooks are the two bugs that cannot be fixed after the fact. A distant region adds about 0.3 s of network per query. |
| D32 | **The app runs on Cloudflare Workers** through the OpenNext adapter, with `cacheComponents` and `partialPrefetching` on and the read-only static-assets incremental cache (the default dummy cache hangs the prerendered page). Cloudflare Email Routing turns the owner's domain into the forwarding address (a Worker posts each forwarded bill to the app); a Cron Trigger calls the app daily (06:00 Tokyo) so the Supabase project never pauses (free projects pause after 7 idle days) and runs reminders. The owner runs `wrangler login` and sets Email Routing in the dashboard; Claude never holds a Cloudflare token. The free plan's 10 ms CPU per request means no server-side image or PDF processing: files go to the model as they are. | The owner already uses Cloudflare; it never sleeps, inbound email is free, and it is the long-term home. Vercel would be lower-risk, Render sleeps on the free tier. |
| D33 | **AI keys are the household's, stored in Supabase Vault, and the server's default is capped.** A household that chooses its own model (D56) gives its key in Settings → Your AI model; it is sent once over HTTPS and stored with `vault.create_secret`, so it is encrypted with a key Supabase keeps outside the database; `households.ai_key_secret_id` points at it and `ai_key_hint` shows only its last four characters. It is never logged or returned to the browser. The owner's connection in the server settings (`AI_PROTOCOL`, `AI_BASE_URL`, `AI_API_KEY`, `AI_TEXT_MODEL`, `AI_DOCUMENT_MODEL`) is the **default with a daily per-household cap**, configured explicitly by a positive `AI_DAILY_LIMIT`. A household row lock reserves one call before each model request on the default connection, using the actual date in the household timezone even for a date-anchored demo; calls on a household's own connection do not consume it. Missing settings fail clearly. Vault ownership is checked by household-bound secret name, and reset, upgrade and deletion remove the household key and private documents with retryable database pointers. Document reads and Ask call the model; MCP engine tools do not. This is the monetisation line: free with your own model, a paid plan when we carry the AI cost. Judges never need it. | Pay-per-use AI is the only real cost; users of a money app expect to control it. Vault covers a leaked dump or backup with no extra secret to manage; it does not hide keys from someone holding the database's master credentials, which an app-held key would; acceptable for now. |
| D34 | **Login and first run.** Email → magic link → httpOnly session cookie, 30 days, refreshed silently; no passwords anywhere. The public link offers **Try it**: one tap makes an anonymous session with a fresh copy of Ben's household anchored at Nov 14, 2026 for a reproducible runway (each judge gets their own; approve, watch the webhook land, reset); adding an email turns it into a real account. Onboarding minimum: bank balance and one card (label, closing day, due day, limit optional); PayPal is the env merchant and its invoice history supplies clients and days to pay; forwarding address and AI model are shown but skippable. A partner joins a household through a magic link carrying the household id; `members` and `users` already allow several people in one household, the invite screen comes later. | Under a minute to the sentence; a shared demo collides between judges. |
| D35 | **Updates are in-app.** Every change is an `events` row (also the Activity list); rows that matter carry `notify = true` and a `read_at`, and a bell in the top bar shows the unread count and the list. Home and To check poll the feed only while something is in flight (mechanics: ARCHITECTURE.md, Updates). Notified events: invoice paid (verified webhook), a new To check row, statement closes today, bill due in 3 days, client past their usual date, the sentence flipping between fine and short. | D36 | **Reading pipeline.** Upload a photo/PDF or forward to the household’s opaque address. Store the original in a private bucket, return after queuing, and read it in the background through the request’s lifetime hook. The connection's document model (`AI_DOCUMENT_MODEL`, or the household's own, D56) reads photos, PDFs and mail with attachments; its text model (`AI_TEXT_MODEL`, or the household's own) reads plain mail. Validate extracted fields and show them in To check. Confirmation creates a bill or card charge. Rule patches carry forward corrected names, categories, entry types and cards. Amount and date edits apply to the individual document. Reads on the default connection consume the daily household allowance (D33), and all reader invocations are rate-limited. | Nothing enters the numbers before confirmation. Model selection and the forwarding domain require explicit settings. |
| D37 | **Freshness and safety details.** Home refreshes only locally associated sandbox invoice IDs, with a five-minute cooldown that includes failed attempts. Only the designated non-demo household (`PAYPAL_BALANCE_HOUSEHOLD_ID`) can pull the merchant’s available balance. Other households use their own verified credits. Report timestamps and verified payment timestamps prevent stale reports from erasing receipts or counting them twice. A read can close a cancelled invoice. Only a verified webhook marks it paid. Home renders stored amounts with an explicit status when refresh fails. Demo receipts keep the provider’s timestamp in Activity and use a business date no earlier than the scenario date or the invoice send date. Approve carries an idempotency key per draft. Mutating routes check the origin; cookies are same-site. MCP tokens are made in Settings, shown once, stored hashed, revocable, read and draft only. Every browser-facing route has a per-household rate limit, and Try it is capped app-wide (the numbers: ARCHITECTURE.md, Rules the wiring enforces). PayPal toolkit calls time out after 20 s so a hung call cannot hold approval row locks; `PayPal-Request-Id` makes the retry safe. Sign-in links return to `APP_URL` (required setting), never to the request's Origin header; a missing `APP_URL` raises a clear error. The webhook route does not tell anonymous callers why a delivery was rejected; the reason goes to the server log. The AI-key route caps its body at 4 KiB by reading the stream, not by trusting Content-Length. The daily job processes only UUIDs explicitly configured in `CRON_HOUSEHOLD_IDS` and refuses a missing list; it never enumerates every household. It generates `card_statements` rows on each card's closing day from confirmed charges. Confirming a late charge updates its unpaid closed-cycle statement exactly once under the same household lock, including reader confirmations. The FX rate used is stored on each row: PayPal's own when it converts, otherwise a daily reference the cron fetches (source: O9). A hidden reset exists on Try-it households only; the video is recorded on one. | The bugs that are invisible in a demo and fatal in a product. |
| D38 | **Order of work: foundation wiring → functionality (what the user and the agent can do) → UI/UX → security hardening last.** The hardening list is phase J in PLAN.md; the contracts it needs are here. The operator log is one structured line per request (`cf-ray`, route, household UUID, outcome code, duration; never bodies, amounts, emails, names or keys; `cf-ray` shown on error pages; `events` stays the user's audit trail). Migrations follow expand before use, contract after, so they work with the Worker still running. The privacy page names which model host questions and documents go to (D56). Later: an app database role with RLS policies keyed on a per-transaction `app.household_id` as a second wall; a production Supabase project separate from development; an hourly cron that selects non-demo households by local time instead of `CRON_HOUSEHOLD_IDS`; rotation procedure for owner secrets; Pro-plan backups. | The owner chose to prove the product works first; these items are invisible in a demo and expensive to retrofit, so they are listed now and built last. |
| D39 | **Three doors by hand, one function per job.** A client, a bill and a card charge can be typed in (forms on Clients, To check and Coming up); an invoice with no PayPal id can be marked paid outside PayPal, which credits the bank balance; a PayPal-sent invoice is still marked paid only by the verified webhook (D15) and can otherwise only be closed. | D40 | **The in-app agent is a model with tools over the engine.** One tool catalogue (`src/lib/agent/tools.ts`) serves Ask and the MCP server; tools read `MoneyState` through the engine or call the same `src/db` functions as the forms; the model never sees SQL and never does arithmetic, it quotes tool numbers verbatim. Tool output is treated as untrusted data (biller and merchant names came from documents). How a reply is chosen and shown is D60. One catalogue keeps MCP and the app identical. |
| D41 | **A bill repeats monthly or yearly, can change its amount from a date, and can carry a cancel-by date.** `repeat_unit` (`month`, `year`, or null for one-off) with `repeat_day` for monthly; `next_amount_minor` from `next_amount_from`; `cancel_by`. `loadMoneyState` expands a bill's occurrences across the plan window (which can reach past 30 days to the latest card due date) in `repeat.ts`, each with the amount that applies, so the engine maths in `runway.ts` is unchanged. The form, the reader's review card and `add_bill` take the same fields. Rent, phone, insurance, subscriptions, domains and rate resets are entered once. | Without it the runway forgets rent after one month and "you're fine" becomes false; subscriptions inside the card window were missing from card room. Subscriptions, insurance, domains, rent increases, rate resets and rolled-over trials (3.6M a year in the UK alone, gov.uk) are the same shape: a dated obligation with a repeat, a next amount and a date to act by. |
| D42 | **The bank balance can be updated in one line.** Home has a single field; it writes directly with an event recording the old and new values. | D43 | **Planning is pots.** A pot is money set aside with a reason: a name, a target amount and date (optional), the amount saved so far, an optional fill rule (a percentage of each client payment) and an optional member. Money in pots is not safe to spend. The tax pot is the first one: off until the user sets a percentage, never a judgement of their tax position (D7). Money in pots comes off the cash every runway number starts from (`availableCash`), so safe to spend, the low point, card room, the sentence and the options agree; a pot waiting in To check counts for nothing. A client payment (verified webhook, or marked paid outside PayPal) adds each pot's percentage of it to the pot and records an event. Goal pots (a car, a trip) answer "can I afford X by then": the monthly room is what the next 30 days leave over if clients pay as usual (the expected runway's change over 30 days: sent invoices less bills and card statements), and `plan_for`, a read tool of the agent and MCP, returns the amount still needed, the monthly amount needed by a date, the date reached at a monthly pace (the room unless one is given) and whether it fits, with a one-line summary built in code for the model to quote; `add_pot`, a draft tool, puts the pot in To check for the user to confirm, and is offered only when the user talks about saving or a payment just landed and they ask (D6). The Plan page (`/plan`) adds, edits and removes pots; Home shows one line per pot. Moving money between pots, a projection chart and pots per member come later. | A regular person plans purchases and trips, not only the next 30 days; one concept serves both set-aside tax and goals, and it is the user's own plan, never a product (D7). |
| D44 | **One versioned household schema.** A single zod definition, `HouseholdSnapshot` (`src/lib/schema/household.ts`), describes a whole household: the household (name, home currency, time zone, today, bank balance, PayPal balance in the home currency, and the USD rate its money state uses with the day it is from, so an export is self-contained), members, cards, statements, charges, stored bills (one row each, with repeat day and status), clients, invoices, pots, balance updates and document references, with money as integer minor units plus currency and dates as ISO strings. Pending bills, charges and pots are the same lists with `status: pending`, and balance updates carry their status too, so there is no separate pending section. Every object is strict. Version 2 is the current version: the record, plus the other stored kinds of D59 (what the assistant remembers, the pinned canvases and the conversation turns), each in its own versioned schema (D57), and keeps every version 1 field. One function, `loadHouseholdSnapshot` (`src/db/snapshot.ts`), builds it from the database for one household in a read transaction from named columns only, and parses it before returning. Its uses: **Export my data** in Settings (`/api/export`, `no-store`, an attachment named `personal-economy-saver-<household date>.json`) downloads all of it with the household's events added (when memory, canvases or the conversation are kept on the device, the browser adds the device's items to the file before it is saved); **import** (`/api/restore`, `restoreHousehold`) reads a version 2 file into a household that has nothing in it yet and nothing kept on the device (D59; any other household is refused, version 1 files are refused in words). It is not a byte-for-byte copy: the file's owner maps onto the household's owner so the login keeps working, every imported row gets a new id and every reference inside the file (bills and their series, charges and cards, people and shares, invoices and clients, a recipe's client and bill ids, conversations) is mapped through one old to new table, so a file imports while the household it came from still exists, every restored row is `made_by = import` (memory keeps who made it), a file in another currency is refused, and the file's events, documents (so bills and charges lose their document link), the PayPal invoice ids and status (an id from a file must never become a key PayPal's webhooks write to) and the household's own name, time zone, currency and exchange rate are not restored; the read tool `household_snapshot` gives the agent and MCP the record in one call (no events, memory or conversations; at most the 100 most recent rows of each long list, oldest first, with a `truncated` flag per list); and JSON Schemas generated from the same zod definitions (`npm run schema`; the five files and the drift test: ARCHITECTURE.md, Rules the wiring enforces), including `CashFlowEvent` (`src/lib/schema/cash-flow.ts`: one dated in or out as the `timeline` tool returns it, with a `direction`). It never contains the AI key or its Vault id, auth ids, MCP token hashes, webhook payloads or document files (documents appear only as id, kind, status and date). The snapshot is context: answers about spending still come from the engine tools (D40). | One shape for the database, the export, the agent and other apps keeps them consistent and saves the agent tool turns (at most 4, D40).
