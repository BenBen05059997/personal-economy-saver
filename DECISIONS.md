# Decisions

The current decisions, and only those. When PLAN.md, AGENTS.md, ARCHITECTURE.md or any other document disagrees with this file, this file wins and the other gets fixed.

How it is kept: when a decision changes, its row is rewritten to the new decision (or deleted if it no longer applies). Nothing old is kept. The row is updated in the same turn the decision is made, then any document that still says the old thing is fixed.

### How it works

| ID | Decision | Why |
|---|---|---|
| D10 | **Inputs:** a forwarding address and photo/PDF upload. One reader for bills, card-use emails and receipts. Every read goes through a confirmation card; corrections become rules. No Gmail OAuth, no bank or card login; the only connection is PayPal. | Privacy; Gmail read scope needs review and caps test users. |
| D11 | **Runway:** 30 days. Cash = PayPal balance + typed bank balance. Out = bills and card statements on their due dates. In = invoices at expected (sent + the client's median days to pay) and worst case (sent + their slowest). Alerts fire on the worst case. USD households' invoice forecasts round to cents, not whole dollars. | Believable, computed from PayPal history; fits one screen. |
| D12 | **The PayPal action is getting paid, not paying bills:** invoice finished work, remind late clients. The agent holds only draft/read tools (the toolkit's draft/send split is the approval gate); send and reminders run server-side after the user taps Approve. A verified webhook closes the loop. Lint enforces the split: only `src/app/api/approve/route.ts` may import the send-capable `runTool` and `deleteSmokeDraft` (`no-restricted-imports` in `economy-saver/eslint.config.mjs`). | Billers aren't PayPal merchants; getting paid is where PayPal is strongest. |
| D13 | **Agent Toolkit used directly** (`PayPalAPI.run()` + tool definitions), not its AI SDK wrapper. The toolkit has no balance or webhook tools, so the balance is a direct REST read (`/v1/reporting/balances`) and webhook verification is a direct REST call. `create_invoice` makes a draft with no due date or payment term, so the expected payment date is the send date plus the client's observed days to pay. Tool errors come back as JSON strings and are shown as they are. | The wrapper is pinned to an old AI SDK. |
| D14 | **Sandbox only, enforced in code.** Every PayPal call stops with a clear error unless `PAYPAL_ENVIRONMENT=SANDBOX`; the only PayPal host in the code is the sandbox; the toolkit is created with `sandbox: true`. | Safety; the toolkit defaults to live. |
| D15 | **Webhooks are verified** with PayPal's signature check before anything changes. A verified delivery, the fully paid invoice transition and its notification commit together. Deliveries are unique on PayPal event id. Partial or pending payments leave the invoice open. The browser never sets payment state. | Trust. |
| D16 | **PayPal fee framing:** help the user keep more of each payout (price the fee in, invoice currency, convert in bulk). Never "leave PayPal". | Biggest single cost for a foreign-paid freelancer; PayPal-judged contest. |
| D17 | **Sandbox setup:** the app "Personal Economy Saver" is on the **Japan Business** sandbox account (Ben); the **US Personal** sandbox account is the client who pays. | How the owner's dashboard is set up. |
| D18 | **Stack:** Next.js 16 (App Router, TypeScript), zod 3, Drizzle ORM, PayPal Agent Toolkit 1.11, Claude as the model through `@anthropic-ai/sdk`. Hosting and data are D31–D33. | Toolkit uses zod 3; Drizzle is thin TypeScript and emits zod schemas the engine already speaks. |
| D31 | **Data lives in Supabase** (free tier), in Northeast Asia (Tokyo, `ap-northeast-1`) through the transaction pooler on port 6543, because the users and Cloudflare's nearest edge are in Japan: Postgres through Drizzle, magic-link login through Supabase Auth, uploads (receipt photos, PDFs, forwarded emails) in Supabase Storage. The current schema has 21 tables: households, members, users, paypal_connections, clients, invoices, bills, cards, card_statements, charges, documents, readings, rules, events, webhook_deliveries, api_tokens, fx_rates, request_buckets, balance_updates, pots and settlements. Household data queries require `household_id`; verified deliveries for an unknown invoice can be recorded without a household and do not affect money state. Money is integer minor units plus currency, never floats; the FX rate is stored on each conversion; webhook_deliveries is unique on PayPal's event id; "the 27th" is the household's time zone. One PayPal merchant via env keys (per-user Connect with PayPal needs partner approval); `paypal_connections` is per member and has a `merchant_id` column, so per-user Connect is later a change of source, not a rewrite. A delete-my-household route exists. | One free account gives database, login and files; no card needed. Integer money and idempotent webhooks are the two bugs that cannot be fixed after the fact. A distant region adds about 0.3 s of network per query. |
| D32 | **The app runs on Cloudflare Workers** through the OpenNext adapter, with `cacheComponents` and `partialPrefetching` on and the read-only static-assets incremental cache (the default dummy cache hangs the prerendered page). Cloudflare Email Routing turns the owner's domain into the forwarding address (a Worker posts each forwarded bill to the app); a Cron Trigger calls the app daily (06:00 Tokyo) so the Supabase project never pauses (free projects pause after 7 idle days) and runs reminders. The owner runs `wrangler login` and sets Email Routing in the dashboard; Claude never holds a Cloudflare token. The free plan's 10 ms CPU per request means no server-side image or PDF processing: files go to Claude as they are. | The owner already uses Cloudflare; it never sleeps, inbound email is free, and it is the long-term home. Vercel would be lower-risk, Render sleeps on the free tier. |
| D33 | **AI keys are the user's, stored in Supabase Vault.** Settings has an Anthropic API key field; the key is sent once over HTTPS and stored with `vault.create_secret`, so it is encrypted with a key Supabase keeps outside the database; `households.ai_key_secret_id` points at it and `ai_key_hint` shows only prefix…suffix. It is never logged or returned to the browser. The owner's key in the server secrets is the **default with a daily per-household cap**, configured explicitly by positive `ANTHROPIC_DAILY_READ_LIMIT`. A household row lock reserves one call before each app-side Claude request, using the actual date in the household timezone even for a date-anchored demo. Own-key calls do not consume this allowance. Missing key/quota settings fail clearly. Vault ownership is checked by household-bound secret name, and reset, upgrade and deletion remove the household key and private documents with retryable database pointers. Document reads and Ask call Claude; MCP engine tools do not. This is the monetisation line: free with your own key, a paid plan when we carry the AI cost. Judges never need it. | Pay-per-use AI is the only real cost; users of a money app expect to control it. Vault covers a leaked dump or backup with no extra secret to manage; it does not hide keys from someone holding the database's master credentials, which an app-held key would; acceptable for now. |
| D34 | **Login and first run.** Email → magic link → httpOnly session cookie, 30 days, refreshed silently; no passwords anywhere. The public link offers **Try it**: one tap makes an anonymous session with a fresh copy of Ben's household anchored at Nov 14, 2026 for a reproducible runway (each judge gets their own; approve, watch the webhook land, reset); adding an email turns it into a real account. Onboarding minimum: bank balance and one card (label, closing day, due day, limit optional); PayPal is the env merchant and its invoice history supplies clients and days to pay; forwarding address and AI key are shown but skippable. A partner joins a household through a magic link carrying the household id; `members` and `users` already allow several people in one household, the invite screen comes later. | Under a minute to the sentence; a shared demo collides between judges. |
| D35 | **Updates are in-app.** Every change is an `events` row (also the Activity list); rows that matter carry `notify = true` and a `read_at`, and a bell in the top bar shows the unread count and the list. Home and To check poll every 5 s while a household has a sent invoice with a PayPal ID or a queued/active reader job. Focus and visibility changes share a feed check, and only a changed feed refreshes the page. The feed cursor is the latest event time read from the server. A Try it household's events are stamped on its clock (the demo date at the current time of day), so Activity dates and sorting match the scenario; real households keep real time. Notified events: invoice paid (verified webhook), a new To check row, statement closes today, bill due in 3 days, client past their usual date, the sentence flipping between fine and short. Quiet by default: one notification a day unless money moved. No email digest. Web Push later. | Polling is robust on Workers and needs no RLS for Realtime; the owner chose in-app over email. |
| D36 | **Reading pipeline.** Upload a photo/PDF or forward to the household’s opaque address. Store the original in a private bucket, return after queuing, and read it in the background through the request’s lifetime hook. `ANTHROPIC_DOCUMENT_MODEL` names the model for photos, PDFs and mail with attachments. `ANTHROPIC_TEXT_MODEL` names the model for plain mail. Validate extracted fields and show them in To check. Confirmation creates a bill or card charge. Rule patches carry forward corrected names, categories, entry types and cards. Amount and date edits apply to the individual document. Default-key reads consume the daily household allowance, and all reader invocations are rate-limited. | Nothing enters the numbers before confirmation. Model selection and the forwarding domain require explicit settings. |
| D37 | **Freshness and safety details.** Home refreshes only locally associated sandbox invoice IDs, with a five-minute cooldown that includes failed attempts. Only the designated non-demo household (`PAYPAL_BALANCE_HOUSEHOLD_ID`) can pull the merchant’s available balance. Other households use their own verified credits. Report timestamps and verified payment timestamps prevent stale reports from erasing receipts or counting them twice. A read can close a cancelled invoice. Only a verified webhook marks it paid. Home renders stored amounts with an explicit status when refresh fails. Demo receipts keep the provider’s timestamp in Activity and use a business date no earlier than the scenario date or the invoice send date. Approve carries an idempotency key per draft. Mutating routes check the origin; cookies are same-site. MCP tokens are made in Settings, shown once, stored hashed, revocable, read and draft only. Per-household rate limits a minute: Ask and MCP 30, uploads and document reads 6, PayPal import 2, data export 6, drafts 20, approvals 10; Try it is capped app-wide at 60 new demo households an hour. PayPal toolkit calls time out after 20 s so a hung call cannot hold approval row locks; `PayPal-Request-Id` makes the retry safe. Sign-in links return to `APP_URL` (required setting), never to the request's Origin header; a missing `APP_URL` raises a clear error. The webhook route does not tell anonymous callers why a delivery was rejected; the reason goes to the server log. The AI-key route caps its body at 4 KiB by reading the stream, not by trusting Content-Length. The daily job processes only UUIDs explicitly configured in `CRON_HOUSEHOLD_IDS` and refuses a missing list; it never enumerates every household. It generates `card_statements` rows on each card's closing day from confirmed charges. Confirming a late charge updates its unpaid closed-cycle statement exactly once under the same household lock, including reader confirmations. The FX rate used is stored on each row: PayPal's own when it converts, otherwise a daily reference the cron fetches (source: O9). A hidden reset exists on Try-it households only; the video is recorded on one. | The bugs that are invisible in a demo and fatal in a product. |
| D38 | **Order of work: foundation wiring → functionality (what the user and the agent can do) → UI/UX → security hardening last.** The hardening list is PLAN phase J: a tenant-isolation test across every read in `src/db`; a sweeper that deletes demo households older than N days with their Storage objects; an app-wide daily AI budget in `request_buckets` and per-IP limits on `/api/try` and `/api/auth/link`; an operator log contract (one structured line per request: `cf-ray`, route, household UUID, outcome code, duration; never bodies, amounts, emails, names or keys; `cf-ray` shown on error pages; `events` stays the user's audit trail); retention for raw documents and a trimmed `webhook_deliveries.payload`; the migration-order rule (expand before use, contract after; migrations must work with the Worker still running); a manual encrypted database dump before demo day; a privacy page (what is stored, where, who processes it, for how long, how to delete, including that documents go to Anthropic in the US); a cap on Storage bytes per household (each upload is already capped at 6 MiB); the JSON export is part of the household schema (D44). Later: an app database role with RLS policies keyed on a per-transaction `app.household_id` as a second wall; a production Supabase project separate from development; an hourly cron that selects non-demo households by local time instead of `CRON_HOUSEHOLD_IDS`; rotation procedure for owner secrets; Pro-plan backups. | The owner chose to prove the product works first; these items are invisible in a demo and expensive to retrofit, so they are listed now and built last. |
| D39 | **Three doors by hand, one function per job.** A client, a bill and a card charge can be typed in (forms on Clients, To check and Coming up); an invoice with no PayPal id can be marked paid outside PayPal, which credits the bank balance; a PayPal-sent invoice is still marked paid only by the verified webhook (D15) and can otherwise only be closed. Past PayPal invoices can be imported read-only to seed clients and days-to-pay. Each job has exactly one database function, called by the form (confirmed rows) and by the agent tool (pending rows, through To check). The approve route still sends to `SANDBOX_CLIENT_EMAIL`, so a client's email is display-only until live PayPal. | A real person with a rent bill and no PDF, or a first client, had no way in; two code paths for one job would drift. |
| D40 | **The in-app agent is a model with tools over the engine.** One tool catalogue (`src/lib/agent/tools.ts`) serves `/api/ask` and the MCP server; tools read `MoneyState` through the engine or call the same `src/db` functions as the forms; the model never sees SQL and never does arithmetic, it quotes tool numbers verbatim. Claude through `@anthropic-ai/sdk` (the one client in `src/lib/anthropic.ts`, no retries, shared with the reader), `ANTHROPIC_TEXT_MODEL`, at most 4 tool turns and 20 s, key through `aiKey()` (the user's Vault key or the owner's capped default; asks on the default key count in the daily allowance). When no key is available, ask returns the clear error (rule 10). Writes from the agent are pending rows or drafts; sending stays behind the tap (D12). Tool output is treated as untrusted data (biller and merchant names came from documents). Tests inject a fake transport, like PayPal's. | Judges score PayPal + AI; a regex ask box is the weak point. The engine already does the maths correctly, so the model should only choose and phrase. One catalogue keeps MCP and the app identical. |
| D41 | **Bills can repeat monthly** (and yearly since D48). A bill carries an optional day of the month; `loadMoneyState` expands its occurrences across the plan window (which can reach past 30 days to the latest card due date), so the engine maths in `runway.ts` is unchanged. Paying or confirming one occurrence leaves the next one in place. Rent, phone, insurance and subscriptions are entered once. | Without it the runway forgets rent after one month and "you're fine" becomes false; subscriptions inside the card window were already missing from card room. |
| D42 | **The bank balance can be updated in one line.** Home has a single field; it writes directly with an event recording the old and new values. The agent and MCP get a tool that makes a pending balance update in To check, confirmed with one tap. | The most frequent update a person makes. Voice mishears numbers and the tool is shared with MCP, so the agent never rewrites the one number everything rests on without a tap (keeps D40). |
| D43 | **Planning is pots.** A pot is money set aside with a reason: a name, a target amount and date (optional), the amount saved so far, an optional fill rule (a percentage of each client payment) and an optional member. Money in pots is not safe to spend. The tax pot is the first one: off until the user sets a percentage, never a judgement of their tax position (D7). Money in pots comes off the cash every runway number starts from (`availableCash`), so safe to spend, the low point, card room, the sentence and the options agree; a pot waiting in To check counts for nothing. A client payment (verified webhook, or marked paid outside PayPal) adds each pot's percentage of it to the pot and records an event. Goal pots (a car, a trip) answer "can I afford X by then": the monthly room is what the next 30 days leave over if clients pay as usual (the expected runway's change over 30 days: sent invoices less bills and card statements), and `plan_for`, a read tool of the agent and MCP, returns the amount still needed, the monthly amount needed by a date, the date reached at a monthly pace (the room unless one is given) and whether it fits, with a one-line summary built in code for the model to quote; `add_pot`, a draft tool, puts the pot in To check for the user to confirm, and is offered only when the user talks about saving or a payment just landed and they ask (D6). The Plan page (`/plan`) adds, edits and removes pots; Home shows one line per pot. Moving money between pots, a projection chart and pots per member come later. | A regular person plans purchases and trips, not only the next 30 days; one concept serves both set-aside tax and goals, and it is the user's own plan, never a product (D7). |
| D44 | **One versioned household schema.** A single zod definition, `HouseholdSnapshot` (version 1, `src/lib/schema/household.ts`), describes a whole household: the household (name, home currency, time zone, today, bank balance, PayPal balance in the home currency, and the USD rate its money state uses with the day it is from, so an export is self-contained), members, cards, statements, charges, stored bills (one row each, with repeat day and status), clients, invoices, pots, balance updates and document references, with money as integer minor units plus currency and dates as ISO strings. Pending bills, charges and pots are the same lists with `status: pending`, and balance updates carry their status too, so there is no separate pending section. Every object is strict. One function, `loadHouseholdSnapshot` (`src/db/snapshot.ts`), builds it from the database for one household in a read transaction from named columns only, and parses it before returning. It has three uses: **Export my data** in Settings (a POST form to `/api/export`: same-origin, 6 a minute per household, `no-store`, an attachment named `personal-economy-saver-<household date>.json`) downloads all of it with the household's events added; the read tool `household_snapshot` gives the agent and MCP the whole picture in one call (no events; at most the 100 most recent rows of each long list, oldest first, with a `truncated` flag per list); and a JSON Schema generated from the same definition with `zod-to-json-schema` is committed as `schema/household.v1.json` (`npm run schema`), with a test that fails when it drifts. It never contains the AI key or its Vault id, auth ids, MCP token hashes, webhook payloads or document files (documents appear only as id, kind, status and date). The snapshot is context: answers about spending still come from the engine tools (D40). Import from the same file comes later. | One shape for the database, the export, the agent and other apps keeps them consistent and saves the agent tool turns (at most 4, D40). An export is the most sensitive thing the app produces, so it is scoped, same-origin and never cached. |
| D45 | **Household split: who owes whom.** Every member has a share in basis points, summing to 10,000; adding a member splits equally until the owner changes it in Settings → People. A bill is one member's or shared (`member_id` null), and a shared bill names who pays it (`paid_by_member_id`, which applies to every occurrence of a monthly bill); a card charge can be marked shared and is paid by the card's owner. The balance is pure maths in `lib/money/split.ts`: each confirmed shared item dated after the last settlement, on or before today and on or after the day the household got its second member, owes the payer the other members' shares at the current shares. Home shows one line per transfer ("Wife owes Ben ¥12,400") with Mark settled, which records the transfers with a through date. The runway and the sentence stay one household pool; the split moves no money in the engine. The split appears only when a household has two or more members, so Ben's demo is unchanged. Agent and MCP read tool `who_owes_whom`; `add_bill` takes shared and paid by, `log_charge` takes shared. | Couples and families share bills unevenly and want a fair number without a spreadsheet. One pool keeps one sentence (D28); counting from the last settlement means a change of shares never rewrites what was settled. |
| D46 | **One category list and a business share on every bill and charge.** Fourteen fixed categories, the same in every country, keyed in code (`src/lib/money/categories.ts`: housing, utilities, phone_internet, subscriptions, food, transport, travel, health, insurance, family_shared, government_tax, business_tools, debt, other) with their labels; stored as the key on `bills.category` and `charges.category` under a check constraint. Every bill and charge also carries `business_bp` (0 = personal, 10000 = business, between = a mixed share such as 30% of rent), default 0. The app proposes both: a pure keyword table (`lib/money/categorise.ts`) from the biller or merchant name first, the agent for unknown names once the AI settings exist; a proposal the table is not sure of pre-selects nothing, so the user chooses. The user confirms or corrects in the form or in To check; nothing is categorised silently.
